# Report 评估

这里有两类不同目的的评估：合成场景检查基本行为；尚未参与提炼的真实样本检查个人适配程度。目前已吸收 5 条历史素材和 1 条用户修订，它们全部用于规则提炼，不是保留测试，也不等于 6 个独立案例。尚无个人风格通过率。实际完成的检查见 [验证记录](validation-notes.md)。

## 合成场景

[cases.json](cases.json) 中每条案例都显式标为 `synthetic: true`，由助手构造，不是用户经历、偏好或真实汇报。它们覆盖老板 / 同事与日报 / 阶段进度 / 成果 / FYI 的组合，以及缺失信息、完成状态、冲突样本和任务范围。

每条用例包含：

- `id`、`synthetic`、`mode`：标识、合成标记和生成或提炼模式。
- `input`：交给执行者的情景与输入。
- `must`：结果应满足的可观察要求。
- `must_not`：不能发生的错误。

手工运行方法：

1. 给独立执行者加载待测的 Report 技能，以及该用例的 `mode` 和 `input`。说明这是合成测试，仅返回文本；不要提供 `must`、`must_not` 或预期结论。
2. 记录技能版本、测试用例 ID、执行环境或模型、日期、完整输出。不要调用真实发送、购买或修改业务状态的工具。
3. 另一轮对照 `must`、`must_not` 检查输出，记录“通过 / 未通过 / 无法判断”及对应文本证据。
4. 只针对观察到的行为修正规则，并复查该问题和可能受影响的其他情景。

没有标准成稿；结构和措辞可以不同。检查的是事实与意图，不是特定标题、词语或固定模板。涉及数字时允许准确且有必要的推导，但不能把推导、预测或目标冒充实际观测值。

用例通过只能说明这些合成情景下的行为符合要求，不能证明技能理解了用户的语气。这里没有自动评测器；不要把仅检查 JSON 格式称作行为测试通过。

## 真实样本与个人风格

第一批素材可以留出约两条，或用后续的新任务验证。保留样本在测试前不得进入规则提炼；负责生成的执行者只看当时背景、对象、目的及事实，不看实际终稿、取舍解释或基于它提炼的规则。资料不足时记录该限制。

已经用于提炼的样本只能做回顾检查，不能作为独立验证。一次案例经过反馈和改写后，改写稿可以判断是否解决了问题，但下一次独立评估需要新案例。

按以下顺序评估，遇到事实错误先修正事实：

| 维度 | 查看什么 |
| --- | --- |
| 事实与承诺 | 数字、归因、完成状态、负责人、时间、预测是否准确 |
| 沟通目的 | 对方是否能理解现状，明确需要知道或执行的事情 |
| 信息取舍 | 先后顺序、详略、删减和解释程度是否符合用户判断 |
| 表达习惯 | 语气、长度、句式、格式是否自然，是否靠重复口头禅伪装相似 |

用户可直接改稿，并选择“可直接发 / 小改可发 / 需要重写”。保留具体修改和适用条件比单个总分更有用。可使用 [反馈模板](../../templates/report-feedback.md)。

原始真实样本、用户反馈和生成的工作汇报不默认放入版本库；按根目录说明保存到忽略的本地位置。若需要记录评估摘要，先移除敏感事实，只保留必要的结论和可追溯的本地样本 ID。
