# 个人汇报规则档案

状态：**已吸收日报、阶段汇报及同事资料请求改稿，持续校准**。版本 v0.5，2026-09-21。

已纳入 5 条历史样本和 3 条用户修订助手稿，合计 8 条：给 boss 的日报 4 条、会后 recap 1 条、阶段汇报 1 条、回复同事调研问题 1 条、向同事索取资料 1 条。它们不是 8 个完全独立案例。维护 9 条主规则；新增 R-009 记录同事资料请求的局部改稿观察，供相似情境参考，不扩展成全场景要求。尚无独立保留评估，不报告相似度百分比。

证据索引及必要摘录见 [evidence.md](evidence.md)。原始材料留在本地，生成器只需本档案和按需读取的摘录。当前任务的事实不能从这些历史材料里补取。

## 用户已明确的目标

- 将工作模式沉淀为多个 skills，先建设 report。
- 接收背景后，根据对象和情境生成符合本人语气与思路的汇报。
- 包含老板、同事；日报、阶段进度、成果展示和 FYI，后续可扩展。

功能范围不等于证据覆盖。尚不足以推断正式成果展示、独立 FYI 或所有同事关系下的完整风格。

## 规则登记方式

真实规则出现时逐条追加，使用稳定 ID。每条只描述一个可观察、能复用的偏好：

```text
规则 ID：R-001
层次：信息取舍 / 顺序组织 / 表达措辞
适用条件：对象、关系、目的、情境、渠道、时期
偏好行为：在该条件下，倾向如何处理
理由：用户原话或有依据的简短解释；未知写未知
来源：用户明确说明 / 案例观察 / 用户改稿
证据：样本 ID 与支持该规则的脱敏摘录或修改位置
反例及例外：不适用情境、相反样本或尚未解释的冲突
状态：候选 / 多案例支持 / 用户确认 / 已替代
更新时间：日期
替代关系：如有，注明替代或被替代的规则 ID
```

“多案例支持”不等于用户确认。一个真实案例可支持局部候选，不能自动升级成全局习惯。用户明确表达一个范围清楚的偏好，可以直接登记为用户确认。

规则应在本文件内包含足够的脱敏依据，保证整个 report 目录可独立使用。大量精选案例确有必要时，再建立本目录下的案例文件并链接；不要要求生成器读取仓库之外的私密原始材料。

## 当前有效个人规则

### R-001：给 boss 的日报固定四段

- 层次：顺序组织。适用：给当前 boss 的每日工作汇报。
- 行为：保留「一、完成事项」「二、核心认知」「三、现存卡点」「四、明日计划」的顺序，段内用简短编号。没有材料的栏目可简短注明信息不足，不凑数、不编造完成事项。
- 同类日报写法：明日计划倾向任务名短语，如「〔事项〕框架搭建」「〔事项〕框架和数据缺口整理」，少写重复解释。依据 S-002、S-006，不要求逐字复用。
- 理由与证据：S-002、S-004、S-005 均使用这四段；用户明确解释为「日报硬性格式」「硬性格式」。这是该工作情境的格式要求，不是所有写作的审美偏好。
- 状态：用户确认。更新：2026-09-17。
- 例外：会后 recap 使用 R-006；同事回复、FYI 不自动套用日报格式。

### R-002：语气软，内容实

- 层次：表达措辞。适用：给 boss 的工作汇报和协助请求。
- 行为：用温和、自然的开头和请求句，事实、结果、未知与下一步说具体；避免一整段生硬的公文语气。柔和语气不降低事实准确性，也不堆叠谦辞或撒娇措辞。
- 理由与证据：S-002 明确「语气软，内容实」；S-005 明确「较软语气」，并以「我想知道……一般由哪个团队负责呀？」表达疑问。
- 状态：用户确认。更新：2026-09-17。
- 例外：不能推断所有对象都接受同一亲疏程度；表情、语气词只在语境自然时使用。

### R-003：给 boss 汇报项目状态，降低理解门槛

- 层次：信息取舍。适用：给 boss 的日报，尤其从技术对话或群聊整理时。
- 行为：完成事项概括今天实际做过的工作；核心认知提炼项目推进到了哪里、这意味着什么；卡点说明尚缺什么，以及需要协调的动作。避免复述操作步骤、许可代码、注册字段和聊天流水。
- S-006 的改稿校准，限同类 boss 日报：完成事项优先使用工作事项名，如「〔事项〕审批跟进」，不在该栏展开检索、梳理、整理问题等过程。核心认知在事实支持时先写推进程度，再写沟通状态和待核实项；不要因尚有未决项而把已有进度笼统写成“只有初步线索”。卡点可写成「与〔已知对接方〕进一步明确……」等动作，对接方和行动仍需有依据。
- 理由与证据：本轮用户明确「日报不只是汇报我做了什么，同时也是给boss汇报项目进度」「内容不用太过细节，要降低boss的理解门槛」；S-002 把英文审批状态补成「原则批准并附少量修改意见」，把专业图纸补成易理解的基础标准说明。
- 状态：用户确认。更新：2026-09-17。
- 例外：保留会改变判断的不确定性与依赖；用户需要依据时再展开。同事推进可以作为项目状态，但不能改写成用户本人已完成的工作。
- 事实边界：S-006 的“流程基本清晰”和“邮件已发送、等待回复”是那次任务的新信息，不是把不确定写成确定的风格指令；没有依据时不能套用这些状态。

### R-004：回应同事时先回答问题，再补充细节

- 层次：顺序组织。适用：同事询问相关调研进展，用户掌握部分信息时。
- 行为：先说明自己能提供哪部分进展，再分段补充依据、项目含义及待核实项。必要时先限定问题范围，避免把局部发现说成全面掌握。
- 理由与证据：S-001 开头为「如果姐姐说的是……的话，我可能有一点进展。」用户解释「先回答问题，再补充细节。降低对方的理解成本」。
- 状态：用户确认。更新：2026-09-17。
- 例外：「姐姐」仅反映该样本中熟悉同事的称呼，不能扩展到其他同事或 boss；不是所有内容都要加「可能」「一点」。

### R-005：分段便于扫读，不写密集长段

- 层次：表达与排版。适用：微信等工作消息，尤其把专业材料转换为汇报时。
- 行为：将结论、解释、限制拆开，按阅读任务分段或列点；避免把所有细节压进一段，即使逻辑完整也要让对方容易看。
- S-006 的局部观察：有已知、易懂的中文名称时，先写中文再括注必要缩写，帮助 boss 理解。不为套格式自创译名；不把本次省略句号或空行数量固化。
- 理由与证据：S-001 明确将一段密集 AI 原稿标为「不像我，是AI写的，语气太生硬，阅读难」；实际采用的版本先给回应，再分别写依据和限制。
- 状态：用户确认。更新：2026-09-17。
- 例外：不等于所有消息必须很短或每句都单独换行；样本本身允许任务需要的较长解释。

### R-006：会后 recap 按任务分工

- 层次：顺序组织。适用：boss 布置新任务，同时需要跟进旧任务的会后复盘。
- 行为：以工作事项为主项，再分「我这边」「需要您协助」，明确自己的动作、需要对方确认的口径和协调的数据。旧任务继续跟进内容另行归纳。
- 理由与证据：S-003 用户解释「硬性格式，分工明确」，样本逐项区分自己的底稿和框架工作，以及 boss 确认范围、口径、协调数据的工作。
- 状态：用户确认。更新：2026-09-17。
- 例外：只用于该类 recap，不覆盖 R-001 的日报四段。历史任务、金额、待办不能自动进入新文案。

### R-007：熟悉的称呼与直接但温和的协助请求

- 层次：表达措辞。适用：当前已建立关系的 boss。
- 行为：日报可沿用「〔称呼〕好～我来同步今日工作内容。」；会后可用「老师好～我来 recap 一下接下来的工作」。需要协助时用「想请您……」「需要您协助……」「烦请您……」并接具体动作。
- S-006 的改稿校准：自己有可先推进的工作、boss 可并行准备协调时，先说自己的动作，再接「也麻烦老师准备……」。体现双方并行推进，不把“准备联系”加码成要求立即安排。用户写过「我努力将……做出来」，可参考其主动承担和温和表达，不固定使用“努力”、不升级为保证完成。真实存在前置依赖时照实说明。
- 理由与证据：S-002、S-004、S-005 的日报开场一致；S-003 有「需要您协助」「烦请您」等表达。收件人具体称呼由当前上下文确定。
- 状态：多案例支持，未要求逐字固定。更新：2026-09-17。
- 例外：用户指定其他开头时遵从本次要求；不向新收件人自动使用「老师」称呼，不固定添加问候或语气词。

### R-008：阶段测算汇报直接报进展，分清假设、卡点与数据需求

- 层次：顺序组织、信息取舍与表达。适用：给当前 boss 同步测算框架进展，并请求补充数据的阶段沟通。
- 来源与状态：S-007 用户修订助手稿的局部观察；没有逐项解释理由，限相似情境参考，其他阶段汇报仍需按目的判断。更新：2026-09-20。
- 开场可用「老师好～向您同步〔主题〕的进展」，少写“我来”“一下”等重复铺垫。可参考「目前进展／现存卡点／需要补充的数据」三段；这次用户保留了该结构，不代表所有阶段沟通必须三段。
- 已由用户给定的结论直接表达，减少反复的“目前”“按当前口径”。暂定数量保留“暂按”，估算结果保留“约”等必要限定；不能从删除冗词学成删除所有不确定性。
- 在该 boss 熟悉的测算语境里，优先保留用户选用的 m美元等金额单位，不主动改成“万美元”。这是表达单位偏好，不改变金额、币种、精度或支出与折旧的区别；对不熟悉缩写的读者再作必要解释。
- 用户说明沿用模型原假设时，写清「保留原假设，即……」，避免将现有估算全写成“缺数据所以只能暂算”。依然缺少的数据继续列明，不据此宣称已获得预算或假设已验证。
- 卡点解释使用明确因果：原处理方式 → 与当前已知条件不一致 → 因此需要怎样调整。具体原因来自当次输入；不以“有所调整”代替已有的明确原因，也不编造新的年限或会计判断。
- 协助段可参考先说自己的后续工作，再请老师协调数据；附件说明点明测算主题和表格用途，方便识别与查阅已有参数、待补信息。数据清单及其完整边界按当次输入保留，不抽象成其他项目的固定需求。
- 边界：本样本的资本化、费用化、比例、金额、数量及折旧年限仅属本次用户提供的业务口径，不是 skill 验证过的会计准则，也不能带入后续项目。保留的句子不自动成为永久偏好。

### R-009：向同事索取资料，先列需求，再说明已知及待深化处

- 层次：信息取舍与顺序组织。适用：向熟悉同事补充收集资料，用于面向第三方的项目说明；是资料请求，不是给第三方的最终文书。
- 来源与状态：S-008 用户修订 skill 原稿的局部观察，未逐项解释理由；限相似场景参考。更新：2026-09-21。
- 开场交代相关背景、材料用途及需要说明的问题，再进入请求。该稿从“领导让我做〔篇幅〕材料”改为“我需要整理〔材料〕给〔对象〕”，可参考其直接承担任务的表达；不推出不能提领导，也不删除当前明确要求保留的篇幅或交办关系。
- 先按交付目的组织要了解的方向，再另列「我已经有但期望更详实的信息」。已有信息用来标出理解基础及希望核实、细化的部分，不因已有初步信息就不再询问，也不把用户已明确的事实都重新降为未知；没有已知信息时不凑这一段。
- 需要说明风险影响与应对时，围绕困难、影响、应对办法及当前进展提问；运营期问题允许询问未来可能措施。具体船次等个案可放入已知信息或按需追问，不以单个案例替代整体信息需求。问题维度由当次任务决定，不固定为本例的三个方向。
- 需核实的缓释因素仍是询问或假设；用户为调查方向举例不等于该保障已成立。“可能采取”的安排也不改成已落实或风险已消除。该样本的新增业务信息不是可迁移的风格规则。
- 正文可以直接、清楚，同时保留熟悉称呼与亲和收尾；本次删掉开场波浪号不等于禁用语气词。「现成资料先发，我先整理，缺的集中请教」是该稿保留的协作方式，可按需参考，不是固定收尾或新增承诺。
- 例外：回复同事提问仍按 R-004 先回应；不向纯 FYI 或单项确认强加“需求＋已知”的双层结构，也不把「姐姐」用于未建立同等关系的收件人。
