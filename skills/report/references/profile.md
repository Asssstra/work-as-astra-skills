# 个人汇报规则档案

状态：**已完成首批提炼，待实战反馈校准**。版本 v0.2，2026-09-17。

真实样本数：5；覆盖给 boss 的日报 3 条、会后 recap 1 条、回复同事调研问题 1 条。当前有效规则 7 条，其中 6 条有用户明确解释，1 条由多条样本支持。尚无独立保留评估，不报告相似度百分比。

证据索引及必要摘录见 [evidence.md](evidence.md)。原始材料留在本地，生成器只需本档案和按需读取的摘录。当前任务的事实不能从这些历史材料里补取。

## 用户已明确的目标

- 将工作模式沉淀为多个 skills，先建设 report。
- 接收背景后，根据对象和情境生成符合本人语气与思路的汇报。
- 包含老板、同事；日报、阶段进度、成果展示和 FYI，后续可扩展。

功能范围不等于证据覆盖。尚不足以推断正式成果展示、独立 FYI 或所有同事关系下的完整风格。

## 规则登记方式

真实规则出现时逐条追加，使用稳定 ID。每条只描述一个可观察、能复用的偏好：

```text
规则 ID：R-001
层次：信息取舍 / 顺序组织 / 表达措辞
适用条件：对象、关系、目的、情境、渠道、时期
偏好行为：在该条件下，倾向如何处理
理由：用户原话或有依据的简短解释；未知写未知
来源：用户明确说明 / 案例观察 / 用户改稿
证据：样本 ID 与支持该规则的脱敏摘录或修改位置
反例及例外：不适用情境、相反样本或尚未解释的冲突
状态：候选 / 多案例支持 / 用户确认 / 已替代
更新时间：日期
替代关系：如有，注明替代或被替代的规则 ID
```

“多案例支持”不等于用户确认。一个真实案例可支持局部候选，不能自动升级成全局习惯。用户明确表达一个范围清楚的偏好，可以直接登记为用户确认。

规则应在本文件内包含足够的脱敏依据，保证整个 report 目录可独立使用。大量精选案例确有必要时，再建立本目录下的案例文件并链接；不要要求生成器读取仓库之外的私密原始材料。

## 当前有效个人规则

### R-001：给 boss 的日报固定四段

- 层次：顺序组织。适用：给当前 boss 的每日工作汇报。
- 行为：保留「一、完成事项」「二、核心认知」「三、现存卡点」「四、明日计划」的顺序，段内用简短编号。没有材料的栏目可简短注明信息不足，不凑数、不编造完成事项。
- 理由与证据：S-002、S-004、S-005 均使用这四段；用户明确解释为「日报硬性格式」「硬性格式」。这是该工作情境的格式要求，不是所有写作的审美偏好。
- 状态：用户确认。更新：2026-09-17。
- 例外：会后 recap 使用 R-006；同事回复、FYI 不自动套用日报格式。

### R-002：语气软，内容实

- 层次：表达措辞。适用：给 boss 的工作汇报和协助请求。
- 行为：用温和、自然的开头和请求句，事实、结果、未知与下一步说具体；避免一整段生硬的公文语气。柔和语气不降低事实准确性，也不堆叠谦辞或撒娇措辞。
- 理由与证据：S-002 明确「语气软，内容实」；S-005 明确「较软语气」，并以「我想知道……一般由哪个团队负责呀？」表达疑问。
- 状态：用户确认。更新：2026-09-17。
- 例外：不能推断所有对象都接受同一亲疏程度；表情、语气词只在语境自然时使用。

### R-003：给 boss 汇报项目状态，降低理解门槛

- 层次：信息取舍。适用：给 boss 的日报，尤其从技术对话或群聊整理时。
- 行为：完成事项概括今天实际做过的工作；核心认知提炼项目推进到了哪里、这意味着什么；卡点说明尚缺什么，以及需要协调的动作。避免复述操作步骤、许可代码、注册字段和聊天流水。
- 理由与证据：本轮用户明确「日报不只是汇报我做了什么，同时也是给boss汇报项目进度」「内容不用太过细节，要降低boss的理解门槛」；S-002 把英文审批状态补成「原则批准并附少量修改意见」，把专业图纸补成易理解的基础标准说明。
- 状态：用户确认。更新：2026-09-17。
- 例外：保留会改变判断的不确定性与依赖；用户需要依据时再展开。同事推进可以作为项目状态，但不能改写成用户本人已完成的工作。

### R-004：回应同事时先回答问题，再补充细节

- 层次：顺序组织。适用：同事询问相关调研进展，用户掌握部分信息时。
- 行为：先说明自己能提供哪部分进展，再分段补充依据、项目含义及待核实项。必要时先限定问题范围，避免把局部发现说成全面掌握。
- 理由与证据：S-001 开头为「如果姐姐说的是……的话，我可能有一点进展。」用户解释「先回答问题，再补充细节。降低对方的理解成本」。
- 状态：用户确认。更新：2026-09-17。
- 例外：「姐姐」仅反映该样本中熟悉同事的称呼，不能扩展到其他同事或 boss；不是所有内容都要加「可能」「一点」。

### R-005：分段便于扫读，不写密集长段

- 层次：表达与排版。适用：微信等工作消息，尤其把专业材料转换为汇报时。
- 行为：将结论、解释、限制拆开，按阅读任务分段或列点；避免把所有细节压进一段，即使逻辑完整也要让对方容易看。
- 理由与证据：S-001 明确将一段密集 AI 原稿标为「不像我，是AI写的，语气太生硬，阅读难」；实际采用的版本先给回应，再分别写依据和限制。
- 状态：用户确认。更新：2026-09-17。
- 例外：不等于所有消息必须很短或每句都单独换行；样本本身允许任务需要的较长解释。

### R-006：会后 recap 按任务分工

- 层次：顺序组织。适用：boss 布置新任务，同时需要跟进旧任务的会后复盘。
- 行为：以工作事项为主项，再分「我这边」「需要您协助」，明确自己的动作、需要对方确认的口径和协调的数据。旧任务继续跟进内容另行归纳。
- 理由与证据：S-003 用户解释「硬性格式，分工明确」，样本逐项区分自己的底稿和框架工作，以及 boss 确认范围、口径、协调数据的工作。
- 状态：用户确认。更新：2026-09-17。
- 例外：只用于该类 recap，不覆盖 R-001 的日报四段。历史任务、金额、待办不能自动进入新文案。

### R-007：熟悉的称呼与直接但温和的协助请求

- 层次：表达措辞。适用：当前已建立关系的 boss。
- 行为：日报可沿用「〔称呼〕好～我来同步今日工作内容。」；会后可用「老师好～我来 recap 一下接下来的工作」。需要协助时用「想请您……」「需要您协助……」「烦请您……」并接具体动作。
- 理由与证据：S-002、S-004、S-005 的日报开场一致；S-003 有「需要您协助」「烦请您」等表达。收件人具体称呼由当前上下文确定。
- 状态：多案例支持，未要求逐字固定。更新：2026-09-17。
- 例外：用户指定其他开头时遵从本次要求；不向新收件人自动使用「老师」称呼，不固定添加问候或语气词。

## 待确认观察

### C-001：通过相关提问体现主动学习

S-001 用户不负责该事项，但主动提供掌握的信息；S-005 通过询问某份文件的负责团队获取信息、体现求知。可观察到在特定场景中重视主动参与，但不能据此让每次汇报都加一个问题。

S-005 中「转移注意力」是用户对该次写法的解释，仅保留为局部背景，不升级成隐藏卡点或转移重点的通用策略。本次实战只围绕明确要求安排协助事项。
