# 从样本校准 report

用户可直接粘贴材料并用自然语言解释。不要把填写完整表格作为开始工作的前提。

## 接收与归档

至少尽量获得：实际原文、对象和必要背景、沟通目的；最有助于提取思路的是“当时为什么这样写”。缺失时写未知，优先问会影响解释的那一项。

保留原文换行、标点、称呼和表情，另存结构化说明，不把改写后的文字冒充原样本。支持纯文本或 Markdown；截图先转录，模糊文字不能猜。

使用稳定样本 ID（如 S-001），登记原文来源、是否本人写作、是否代表当前偏好。区分当时可知的事实、当时考虑、事后回看以及对方实际反馈。别人代写、AI 初稿和强制模板都应明确标注。

标签由助手补齐即可：对象、目的、类型、渠道、时期、代表性、来源；允许多选和未知，不要求用户学习机器字段。通常优先确认对象关系和意图，不必把所有标签都问一遍。

原始材料默认进入仓库的 `data-local/`（若当前没有仓库，在当前任务的本地资料区保存并说明位置）。不默认上传。脱敏用稳定代号保留关系、数量级、顺序与因果。具体授权过的脱敏案例可以进入技能参考材料。

## 提炼

把每条样本拆成三个视角：已知事实是什么；选择了什么、舍弃了什么、如何排序；具体如何措辞。

先给少量最有价值的候选规则，并指明依据和适用条件。优先使用用户明确解释、原稿到终稿的删改、跨案例重复出现的行为。没有解释时，可以指出观察，不能虚构动机。

例如，某条短消息不足以证明“用户永远喜欢短句”；同一份内容在私聊和正式评审中的不同写法，可能揭示情境条件。没有写风险也不代表用户偏好隐瞒风险。

按 [profile.md](profile.md) 的格式记录。确认不应变成每条操作都要停下来等审批：用户已明确说明的偏好直接登记；助手推断保留为候选，并在实际改稿中验证。

## 冲突与更新

收到改稿先分清新增事实、进度判断与表达调整。用户在修订版补充了原背景中没有的信息时，按其最新说明更新本次事实，不把事实变化学成可以任意增强确定性的文风。记录“用户修订助手稿”的来源；未改动的部分不自动成为永久偏好。

新旧样本不一致时，先检查对象、渠道、时期、组织要求和当时压力是否不同。能按条件解释就分开保存；仍冲突则保留双方证据，不平均成一种语气。

一次性的篇幅压缩、临时要求或替他人代写，不自动成为长期偏好。用户明确说“以后都这样”时，再按其指定范围更新。

每次更新应说明新增或修改了哪些偏好、证据来自哪里、哪些情境仍无覆盖。把已替代规则标记退出，不与新规则同时应用。

## 验证

留出未参与提炼的真实任务：生成器只看背景和现有 profile，先写文案，再由用户或单独评审者与隐藏原文对照。已经看过并用于提炼的原文不能再算独立测试。

依次检查事实忠实、目的达成、取舍接近程度、措辞自然度。用户可用“可直接发 / 小改可发 / 需重写”，并改掉最不像自己的句子。不要只根据词语重合率或模仿口头禅评分。

合成案例只能检验边界行为与任务覆盖，不能作为个人风格训练证据，也不能证明已经像用户。没有真实评估时如实报告“尚未验证”。
